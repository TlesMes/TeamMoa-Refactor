| Locust | master + **워커 6개** (독립 프로세스) |
| 연결 | 내부 WLAN, RTT 평균 1 ms / 손실 0 % |

### prod 대비 의도적 차이 (전부 기록 대상)

| 항목 | prod | 여기 | 이유 |
|---|---|---|---|
| HTTPS | ALB 종단 | 평문 HTTP | 로컬에 종단점 없음 |
| `SECURE_SSL_REDIRECT` / secure 쿠키 | True | False | 평문 HTTP에서 로그인 불가해짐 |
| DRF throttle | anon 100/h, user 1000/h | **해제** | 아래 |
| `max_connections` | 151 (기본값) | 300 → **2000** | 아래 |

> **throttle 해제가 실험의 전제였다.** 로그인 API는 `AllowAny`(익명)라
> `AnonRateThrottle` 이 **IP 단위**로 걸린다. 부하는 노트북 1대(단일 IP)에서
> 나오므로 시간당 101번째 로그인부터 전부 429가 된다. 해제하지 않으면
> "서버가 언제 무너지는가"가 아니라 **"DRF 카운터가 언제 차는가"** 를 재게 된다.
> 뒤집어 말하면 **prod에서는 인프라 한계보다 이 정책이 먼저 걸린다.**

> **`max_connections` 상향은 2차 한정이다.** 1차에서 커넥션 누수로 301에서
> 500이 터졌는데(7절), 프로세스가 6배면 그 벽에 6배 빨리 닿아 "CPU 천장을
> 걷었을 때 처리량이 어디까지 가는가"를 볼 수 없게 된다. 커넥션을 변수에서
> 빼기 위한 조치이며, **누수 자체는 고쳐야 할 프로덕션 버그다.**

### 먼저 닿은 한계: 단일 프로세스 GIL

**web 컨테이너 CPU가 126~127%에서 완전히 평평하다.** VU 80부터 VU 634까지
부하를 8배 늘리는 동안 1%도 움직이지 않았다.

Daphne는 단일 Python 프로세스다. GIL 때문에 100%가 사실상 천장이고,
127%는 mysqlclient 같은 C 확장이 GIL을 놓는 몫이다. 실측 스레드는 **17개**
(메인 1 + asgiref 워커 16 = `min(32, cpu+4)`).

**반면 호스트 CPU는 25~36%였다.** 앱 프로세스 하나가 꽉 찬 동안 머신에는
여유가 남아 있었다.

> **한계는 하드웨어가 아니라 배포 구성이다.**

**DB는 무릎의 원인이 아니다.** `Threads_running` 이 전 구간 2~4에 머물렀다.
커넥션은 300까지 쌓였지만 실제로 쿼리를 실행 중인 것은 거의 없었다.

## 4. 먼저 닿은 한계: 호스트 물리 코어 6개

**web CPU가 596~622%에서 평평하다.** 프로세스당 약 100%다.
그런데 1차에서 단일 프로세스는 **127%** 까지 갔었다. 프로세스가 스스로 못
올라가는 게 아니라 **못 올라가게 막히고 있다.**

무엇이 막는지는 **프로세스 3개 대조 실험**이 답했다 (같은 VU 400, 같은 초기화 절차).

| | 프로세스당 CPU | 컨테이너 CPU 합계 | RPS |
|---|---:|---:|---:|
| 1프로세스 (1차) | 127 % | 1.51 코어 | 90.9 |
| **3프로세스** | **134 %** | **4.69 코어** (물리 6코어 **이내**) | 222.3 |
| **6프로세스** | **109 %** | **7.59 코어** (물리 6코어 **초과**) | 345.3 |

**3프로세스일 때 프로세스당 134%로 1차(127%)보다도 높다.** 즉 프로세스는 GIL
천장까지 갈 수 있다. 6프로세스에서 109%로 떨어지는 것은 **물리 코어가 없기
때문**이다.

```
Ryzen 5 5600 = 물리 6코어 / 논리 12스레드
물리 6코어 × SMT 실효 계수 1.27 ≈ 7.6 코어   ← 실측 컨테이너 합계 7.59
```

SMT 스레드는 물리 코어가 아니다. 6코어를 넘어서면 같은 물리 코어를 둘이
나눠 쓰게 되고 실효 성능은 1.2~1.3배까지만 늘어난다.

이 때문에:
- 프로세스를 2배(3→6)로 늘렸는데 처리량은 **1.55배**
- 요청당 CPU가 부하와 함께 **12.7 ms → 17.9 ms** 로 상승 (SMT 경합 비용)
- 호스트 CPU 80%는 "여유 20%"가 아니라 **SMT 스레드가 남은 것**이지 실효 여력이 아니다

### 병목 후보 판정

| 후보 | 판정 | 근거 |
|---|---|---|
| 프로세스별 GIL | ❌ | 3프로세스에서 134%까지 갔다. 천장 아님 |
| DB | ❌ | 처리량에 정비례(9%→103%)하고 `Threads_running` 2~3. 포화 아님 |
| Nginx | ❌ | 최대 11 % (0.11 코어) |
| 네트워크 | ❌ | 6절 |
| 생성기 | ❌ | 6절 |
| **호스트 물리 코어** | ✅ | **7.59 코어에서 멈춤 = 물리 6코어 + SMT의 실효 상한** |

## 5. 요청당 CPU — 산술이 맞는다

| 구성 | RPS | web 코어 | 요청당 CPU¹ |
|---|---:|---:|---:|
| 1차 (단일, VU 90) | 90.9 | 1.27 | 14.0 ms |
| 2차 (6개, VU 25) | 32.2 | 0.41 | 12.7 ms |
| 2차 (6개, VU 300) | 364.5 | 5.96 | 16.4 ms |
| 2차 (6개, VU 600) | 348.4 | 6.22 | 17.9 ms |

¹ Locust 요청 1건 기준. 홈 태스크(`/` → 302 → `/teams/`)는 서버에 2번 왕복하므로
Locust 요청 1건이 서버 요청 약 1.25건에 해당한다. 절대치가 목적이 아니라 배율과
일관성이 목적이므로 이 문서 전체에서 RPS는 Locust 집계값으로 통일한다.

요청당 CPU가 13~18 ms 로 일정하다. 즉 **처리량 = 쓸 수 있는 코어 ÷ 요청당 CPU**
라는 단순한 관계가 전 구간에서 성립한다. 천장이 코어 수로 결정된다는 것을
곡선과 독립적으로 뒷받침한다.

## 7. 발견한 프로덕션 버그 — MySQL 커넥션 누수

1차 VU 634에서 에러율 19.89 %가 났다. **원인은 지연이 아니라 커넥션 고갈이다.**

| 측정 | 값 |
|---|---|
| 요청 20건 → 신규 커넥션 증가 | **22** (재사용 0) |
| 테스트 중 총 커넥션 생성 | **122,324** |
| `Max_used_connections` | **301** (= 상한 300 + SUPER 예약 1) |
| `Connection_errors_max_connections` | **2,914** |
| 부하 종료 6분 후 잔존 커넥션 | **73개, 전부 Sleep, 최고령 384초** |
| `wait_timeout` | **28,800초 (8시간)** |

django.log: `Too many connections` 779건, `OperationalError` 604건,
`Internal Server Error` 312건.

**`CONN_MAX_AGE = 600` 이 전혀 동작하지 않는다.** 요청마다 커넥션을 새로 열고
반납하지 않는다. 상한에 닿으면 이후 모든 접속이 거부되어
`OperationalError: Too many connections` → **HTTP 500** 이 된다.

2차에서 상한을 2000으로 올리자 **VU 600에서도 에러율 0 %** 였다 — 진단이
맞았다는 확증이다. 동시에 커넥션은 878까지 쌓였다(프로세스가 6배면 누수도 6배).

> ⚠️ **프로덕션의 `max_connections` 는 설정되어 있지 않아 MySQL 기본값 151이다.**
> 이 멀티프로세스 구성을 그대로 EC2에 올리면 **VU 100도 못 버티고 500이 터진다.**
> **누수 수정이 멀티프로세스 배포의 전제 조건이다.**

## 8. 측정 신뢰성 — 실패와 정정 이력

이 실험에서 **측정 자체가 여러 번 틀렸다.** 결론만큼 이 과정이 중요하다고 보아
그대로 남긴다.

### ① 서버 지표가 통째로 비어 있었다

수집기가 호스트 셸의 `$env:DB_ROOT_PASSWORD` 를 참조했는데 값이 없어 조용히
기본값으로 떨어졌고, MySQL 커넥션이 **전 구간 −1** 로 기록됐다. DB가 먼저
한계에 닿았는지 판정하는 핵심 지표가 통째로 빈 채였다.
→ 컨테이너 환경변수에서 직접 읽고, 시작 시 프로브 1회로 수집 가능 여부를
확인해 실패하면 경고하도록 고쳤다.

### ② 같은 조건인데 결과가 16 % 흔들렸다

2차 직후 같은 VU 400을 재측정했더니 RPS 286 → 241, p95 1,143 → 1,792 ms 였다.
처음엔 누수된 커넥션 749개 탓으로 판단했으나 **틀렸다.**

실제 원인은 **호스트에서 돌고 있던 게임과 브라우저**였다.
측정 전 점검을 만들어 돌리자마자 나왔다:

```
StarRail  1.11 코어
chrome    1.91 코어 (4개 프로세스 합)
─────────────────
합계      약 3.0 코어 = 12스레드의 25 %
```

2차에서 컨테이너 합계가 약 700 %인데 호스트가 89 %로 3.7코어가 설명되지 않았다.
Docker Desktop 오버헤드로 추정했는데 그것도 틀렸다. 대부분이 게임과 브라우저였다.
이걸 종료하자 같은 구성에서 RPS가 **241 → 345** 로 올랐다.

→ 수집기가 측정 시작 시 프로세스별 CPU를 기록하고(`host_processes_<stage>.txt`),
무관한 부하가 0.3코어를 넘으면 경고하도록 했다.

**1차 측정은 이 오염 전에 끝났고, 무엇보다 호스트 CPU가 25~36%로 앱이 호스트에
막히지 않았으므로 결론이 바뀌지 않는다.** 2차만 재측정했다.

### ③ 사다리가 생성기 재부팅으로 끊겼다

VU 400 도중 생성기가 재부팅됐다(05:28:23). 서버는 건드리지 않은 채였고,
VU 400/600만 이어서 측정했다.

재개 시점 상태 차이:

| | VU 300 종료 직후 | 재개 시점 |
|---|---:|---:|
| MySQL 커넥션 | 97 | 237 |
| DB 메모리 | 767 MB | 886 MB |

**교차 검증으로 재개의 유효성을 확인했다.** 초기화 직후 독립적으로 측정한
깨끗한 VU 400 기준선(RPS 345.3 / 평균 472.9 ms / p95 730.4 ms)과 비교해
재개된 VU 400 (357.5 / 439.4 / 783.8)이 각각 +3.5 % / −7.1 % / +7.3 % 로
**전부 10 % 이내**였다.

### 그 밖의 정정

- **`analyze.py` 가 가장 중요한 단계를 통째로 누락하고 있었다.** VU가 목표치를
  유지하지 못하는 단계(400→371, 800→634)를 "정상 상태 없음"으로 버렸는데,
  하필 500 에러가 난 구간이었다. 목표의 90 %면 정상 상태로 보도록 고쳤다.
- **생성기 CSV가 cp949로 쓰여** utf-8 디코딩이 실패, 고VU 단계가 누락됐다.
- **수집기 출력이 드라이브 루트로 샜다** (`$PSScriptRoot` 가 비어 `\results\` 로 감).
- **Nginx CPU를 수집하지 않았다.** 2차 중반에 추가.
- **`locust --processes` 가 네이티브 Windows에서 동작하지 않았다.** 조용히 단일
  프로세스로 떨어져 생성기가 1코어만 쓰게 된다. master/worker 수동 기동으로 교체.

## 9. 기존 AWS 측정과의 관계

| | AWS (2025-12-16) | 로컬 (2026-09-11) |
|---|---|---|
| 환경 | ALB + EC2 t3.micro ×2 | 로컬 PC 단일 노드 |
| `wait_time` | `between(2, 5)` → VU당 0.29 RPS | `between(0.5, 1)` → VU당 **1.29 RPS** |
| 최대 VU | 150 | 600 |
| 최대 p95 | 76 ms | 1,712 ms |
| 무릎 | **찾지 못함** | **VU 300~400** |

**AWS 측정이 무릎을 못 찾은 이유가 설명된다.** VU당 부하 밀도가 0.29 RPS
였으므로 150 VU라도 약 **43 RPS** 다. 단일 프로세스 구성의 천장이 91 RPS
였으니, 천장의 절반에도 닿지 못한 상태에서 끝난 것이다.

> **절대값은 비교할 수 없다.** 하드웨어도 프록시 유무도 다르다.
> 비교 가능한 것은 **"부하 밀도가 부족했다"** 는 구조적 사실뿐이다.
>
> 참고로 t3.micro는 버스터블이라 **지속 baseline이 vCPU 0.2개**다.
> 5분짜리 테스트는 크레딧이 바닥나기 전에 끝났으므로, AWS 리포트의 수치는
> **버스트 상태의 값**이며 지속 부하에 대한 답이 아니다.

## 10. 결론

1. **선형 확장 구간은 VU 25~200이다.** 기울기 1.286 RPS/VU, 예측 대비 오차
   ±0.6 % 이내, 그 구간 내내 p95 30~52 ms.
2. **처리량 천장은 364.5 RPS** (VU 300).
   VU 300/400/600 세 점이 348~365 RPS에 평평하게 붙는다.
3. **무릎은 VU 300~400.** p95가 150 ms → 784 ms로 꺾인다.
4. **먼저 닿은 한계는 호스트의 물리 코어 6개다.** GIL도 DB도 네트워크도
   생성기도 아니었다. 프로세스 3개 vs 6개 대조 실험으로 확정했다.
5. **단일 프로세스 대비 4.0배**(90.9 → 364.5 RPS). 1차의 한계는 하드웨어가
   아니라 배포 구성이었다.
6. **프로덕션 버그를 하나 찾았다.** `CONN_MAX_AGE` 가 동작하지 않아 요청마다
   커넥션이 새로 열리고 반납되지 않는다. prod의 `max_connections` 는 기본값
   151이므로 멀티프로세스 배포 전에 반드시 고쳐야 한다.

## 11. 다음에 할 것

아래는 **가설이다.** 같은 중단 조건으로 재측정해야 결과가 된다.

1. **커넥션 누수 수정.** ASGI 경로에서 `close_old_connections` 가 커넥션을
   만든 스레드와 다른 컨텍스트에서 도는지 우선 확인한다. 부수 효과로 요청당
   CPU(13~18 ms)에서 접속·인증 핸드셰이크 비용이 빠지면 천장이 더 오를 수 있다.
2. **prod에 `max_connections` 명시.** 기본값 151은 멀티프로세스 구성에
   맞지 않는다.
3. **N+1 최적화 전후 비교** (`43eefc5` ↔ `41f941c`).
   **해석에 주의가 필요하다.** 이번 측정에서 DB는 한가했고(`Threads_running`
   2~3) 앱과 호스트 CPU가 먼저 포화됐다. 그런 구성에서는 쿼리 수를 줄여도
   무릎이 거의 움직이지 않을 수 있다. 그 경우 "최적화가 무의미했다"가 아니라
   **"현재 병목이 DB가 아니라서 드러나지 않는다"** 가 올바른 결론이다.
4. **더 많은 코어에서 재측정.** 천장이 물리 코어 수로 결정되는 것이 확인됐으므로,
   코어가 늘면 선형 구간이 그만큼 연장될 것이라는 예측이 성립한다.
   이것이 맞는지는 다른 머신에서 확인해야 한다.
