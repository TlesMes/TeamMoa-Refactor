# 서버 측 원인 규명 (2026-09-11)

> 부하 생성기(노트북)에서 무릎이 **VU 90~100**, VU 400부터 **500 대량 발생**이
> 보고됐다. 생성기 CPU와 네트워크는 병목이 아님이 그쪽에서 확인됐다.
> 이 문서는 **서버 PC에서 측정한 원인**이다. 추론이 아니라 카운터와 로그다.
>
> 단계↔VU 매핑은 시각 기준 추정이며, Locust CSV를 받으면 확정한다.

---

## 결론 요약

무릎과 500 에러는 **원인이 다르다.** 하나로 뭉뚱그리면 안 된다.

| 현상 | 원인 | 성격 |
|---|---|---|
| VU 90~100 무릎 | **Daphne 단일 프로세스 CPU 천장** (호스트는 놀고 있음) | 배포 구성 문제 |
| VU 400+ 500 에러 | **MySQL 커넥션 누수 → max_connections 고갈** | **프로덕션 버그** |

## 1. VU 400+ 의 500 에러 — 커넥션 누수

### 측정값

| 지표 | 값 | 출처 |
|---|---|---|
| 요청 20건 → 신규 커넥션 증가 | **22** | `SHOW GLOBAL STATUS LIKE 'Connections'` 전후 비교 |
| 테스트 중 총 커넥션 생성 | **122,324** | `Connections` |
| `Max_used_connections` | **301** | = `max_connections` 300 + SUPER 예약 1 |
| `Connection_errors_max_connections` | **2,914** | 상한 초과로 **거부된** 접속 수 |
| `wait_timeout` / `interactive_timeout` | **28,800초 (8시간)** | `SHOW VARIABLES` |
| 부하 종료 후 잔존 커넥션 | **73개, 전부 Sleep, 최고령 384초** | `information_schema.PROCESSLIST` |

### django.log

```
779  Too many connections
604  OperationalError
312  Internal Server Error
```

### 기전

**`CONN_MAX_AGE = 600` 이 전혀 동작하지 않는다.**
요청 20건에 커넥션이 22개 늘었다 — 재사용이 0이다.
그리고 만들어진 커넥션이 반납되지 않는다. 부하가 끝나고 6분이 지나도
73개가 Sleep으로 살아 있고, `wait_timeout`이 8시간이라 스스로 정리되지도 않는다.

즉 **요청마다 커넥션을 새로 열고 놓지 않는다.** 부하가 지속되면 상한 300에
부딪히고, 그 뒤로는 모든 신규 접속이 거부되어
`OperationalError: Too many connections` → HTTP 500 이 된다.

수집 타임라인에서 `mysql_threads_connected` 가 **301에 고정된 구간**
(01:16:18~01:18:48)이 정확히 500이 쏟아진 단계다.

### 이건 프로덕션에서도 재현된다

테스트 아티팩트가 아니다. EC2도 같은 `prod` 설정, 같은 Daphne 단일 프로세스
구성이다. 트래픽이 낮아 8시간 안에 300에 닿지 못했을 뿐이다.
`CONN_MAX_AGE`를 믿고 있었다면 그 전제가 틀렸다.

> ⚠️ 이 실험에서 throttle을 해제했기 때문에 도달한 것이 아니다.
> throttle은 요청 수를 제한할 뿐, 커넥션이 반납되지 않는다는 사실은 그대로다.

## 2. VU 90~100 의 무릎 — 단일 프로세스 CPU 천장

### 측정값 (30초 버킷 평균, `results/server_continuous.csv`)

| 추정 단계 | 시각 | **web CPU** | host CPU | web MB | conn 최대 |
|---|---|---|---|---|---|
| A (VU 50?) | 01:00:48~01:04:15 | **87 %** | 25 % | 100 | 35 |
| B (VU 100?) | 01:05:18~01:07:43 | **128 %** | 36 % | 130 | 160 |
| C 이후 전 구간 | 01:08 이후 | **126~128 %** | 28~40 % | 130~224 | 계속 상승 |

### 기전

- **web 컨테이너 CPU가 128%에서 완전히 평평하다.**
  Daphne는 단일 Python 프로세스다. GIL 때문에 100%가 사실상 천장이고,
  128%는 mysqlclient 등 C 확장이 GIL을 놓는 구간의 몫이다. 즉 **포화**다.
- 실측 스레드 수 **17개** = 메인 1 + asgiref 워커 16 (`min(32, cpu_count+4)`, cpu=12).
  동시에 처리 가능한 동기 뷰가 16개로 묶여 있다.
- **호스트 CPU는 30~40%에 불과하다.** 12스레드 머신에서 8코어 이상이 놀고 있는데
  앱 프로세스 하나가 꽉 찼다.

VU 50에서 87%, VU 100에서 128%(천장)에 닿았다.
보고된 무릎 위치(VU 90~100)와 일치한다.

**한계는 하드웨어가 아니라 배포 구성이다.**

### DB는 무릎의 원인이 아니다

`Threads_running` 은 전 구간 **2~4** 에 머물렀다.
커넥션은 300까지 쌓였지만 실제로 쿼리를 실행 중인 것은 거의 없었다.
`db_cpu` 도 16~26% 수준이다.
→ **DB는 한가했다. 쿼리 성능이 무릎의 원인이 아니다.**

이는 N+1 최적화 전후 비교 실험의 해석에도 영향을 준다.
앱 프로세스가 먼저 포화되는 구성에서는 쿼리 수를 줄여도 무릎이 크게
움직이지 않을 수 있다. 대조군 측정 시 이 점을 감안해야 한다.

## 4. 다음에 확인할 것

1. **Locust CSV를 받아 단계↔VU 매핑 확정.** 현재 매핑은 시각 기준 추정이다.
2. **커넥션 누수의 정확한 지점.** `CONN_MAX_AGE`가 무효인 이유를 코드 수준에서
   특정한다. ASGI 경로에서 `close_old_connections` 가 커넥션을 만든 스레드와
   다른 컨텍스트에서 돌 가능성을 우선 확인한다.
3. **무릎을 옮길 수 있는지 검증.**
   - Daphne 인스턴스를 코어 수만큼 띄우고 앞에 Nginx를 두면 무릎이 어디로 가는가
   - `CONN_MAX_AGE=0` 으로 두면 500이 사라지는가 (누수 대신 매번 정리)
   위 둘은 **가설이다.** 같은 중단 조건으로 재측정해서 확인해야 결과가 된다.
